# Design decisions

- Selected a mock-first storefront and payment provider configuration to keep the local demo working without credentials.
- Kept the app in a single-page flow with role-based mock dashboards rather than building a full Supabase-connected runtime before the project is configured.
- Chose a simple product list with a retailer cart and wholesaler/admin dashboards consistent with the PRD’s v1 scope.
- Local mock authentication stores demo accounts and approval status in browser local storage and is demo-only; configured projects use Supabase Auth and Postgres RLS.
- Public registration accepts retailer and wholesaler roles only. Super-admin provisioning is restricted to the service-role seed script.
- Bank details are stored separately and written through the profile-completion RPC; they are not included in business-profile reads.
- Product demo changes are stored in browser local storage. Supabase mode uses the product and master-data tables with RLS and a public-safe wholesaler directory view limited to approved, completed retailer/admin sessions.
- Product photos are resized to a maximum 1200 px longest dimension and compressed to at most 300 KB before upload; v1 stores up to five photos per listing.
- The retailer cart is stored per account (browser storage in demo mode and RLS-protected rows with Supabase). Checkout is authoritative in the `place_order` Postgres RPC: it locks products in a stable order, validates stock/MOQ/seller status, creates one order and one sub-order per wholesaler, and decrements inventory in the same transaction.
- Self-pickup orders receive a short token. Browser-only online payments can be simulated as successful or failed; real Supabase online orders reserve stock for 15 minutes pending the Phase 5 mock payment flow, with `pg_cron` invoking the expiry function every minute. COD order value defaults to ₹5,000 in the database setting `app_settings.cod_order_cap`. Phase 6 adds audited transport-slot administration, booked-slot contact visibility, multi-stop retailer pickup details, and wholesaler-scoped token verification.
- The concurrency integration test uses a dedicated Supabase product with one unit in stock and two approved retailer accounts; it verifies one of two simultaneous checkouts fails and cleans up its fixture order.
- Phase 5 is mock-only by user choice. Mock completion is kept behind a `PaymentProvider` interface; browser-only demos can simulate success/failure locally, while Supabase-backed checkout delegates to an authenticated Netlify function and a service-role-only RPC. Payment-event IDs are idempotent, failed/expired mock payments release stock, and mock payout records remain held until sub-order completion. No live provider, linked-account onboarding, money transfer, or invoice generation is enabled; those require a separate provider decision.
- Phase 7 adds participant-scoped disputes and threaded messages, optional private evidence photos, admin review/resolution, and notifications. Open disputes hold related mock payouts; refund resolution cancels the mock payout record only because live payments are not enabled. Supabase notifications are generated by database triggers and delivered through Realtime; browser-demo disputes and notifications remain local, with photo blobs stored in IndexedDB to avoid localStorage quota limits. Migration `007_disputes_notifications.sql` must be applied after migration 006 before these Supabase features are available. Live migration behavior is unverified.
- Phase 8 provides a paginated super-admin order monitor, account status filters and audited suspend/reinstate actions, COD/transport settings controls, category GST reference rates, dashboard counts, and a view of recent audit records. Grades and units remain versioned v1 masters; GST reference rates are not applied to checkout or invoices. Admin writes use super-admin-only RPCs and are audited in `008_admin_operations.sql`; the browser demo mirrors controls in local storage. We do not expose mock settlement totals as real figures. Live RLS/RPC behavior and three-role end-to-end flows still require manual verification against a configured Supabase project.
